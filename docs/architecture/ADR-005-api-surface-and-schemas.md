# ADR-005: REST API Surface, Pydantic v2 Schemas, and Authentication Architecture

## Status
Accepted (Phase 4 Baseline)

## Context
The Event-Driven Distributed Task Processing Engine requires a comprehensive, standardized, and secure RESTful HTTP API surface (SRS §7, §8, §9, §12, §13, §14, §15, §17). The API must support synchronous and asynchronous task ingestion, queue configurations, worker fleet monitoring, recurring cron/interval job management, dead letter queue (DLQ) operations, real-time WebSocket/SSE telemetry, multi-tenant project isolation with hashed API keys, and rich dashboard metrics (SRS §17.19 Table 18).

To guarantee interoperability and senior-level reliability, all API contracts must be fully specified, typed, and verifiable via Swagger UI / OpenAPI 3.1 before any frontend development begins.

## Decisions

### 1. Standardized Error Response Envelope (SRS §9)
All API error responses (4xx and 5xx) conform strictly to a uniform top-level error envelope:
```json
{
  "error": {
    "code": "MACHINE_READABLE_CODE",
    "message": "Human-readable explanation.",
    "details": {},
    "request_id": "req-xxxxxx",
    "timestamp": "2026-09-25T12:00:00Z"
  }
}
```
Global exception handlers in `src/api/middleware/error_handler.py` catch `HTTPException`, `RequestValidationError`, domain errors (`TaskNotFoundError`, `InvalidStateTransitionError`, `TaskRateLimitExceededError`), and unhandled exceptions to enforce this format across the entire application.

### 2. Authentication & Tenancy Model (SRS §12)
- **JWT Authentication:** Signed via HMAC-SHA256 (`python-jose`), carrying subject user ID, role (`admin`, `operator`, `viewer`), tenant ID, and permission scopes.
- **API Key Authentication:** Plaintext API keys (`te_live_<random_bytes>`) are displayed **only once** upon generation. The database stores only salted HMAC-SHA256 hashes (`src/security/api_keys.py`) alongside a non-secret prefix (`te_live_...`) for operator identification.
- **Pluggable Auth Modes:** Configurable via `API_AUTH_MODE` (`jwt`, `api_key`, `both`).

### 3. Comprehensive Dashboard Analytics (SRS §17.19 Table 18 & §14.4)
Dedicated endpoints provide specialized data structures for dashboard visualizations:
- `/api/v1/analytics/throughput`: Incoming vs. outgoing tasks/second (dual-line chart).
- `/api/v1/analytics/status-distribution`: Status breakdown distribution (stacked bar/donut).
- `/api/v1/analytics/latency`: P50, P95, P99 percentile distributions for queue wait, execution duration, and end-to-end latency.
- `/api/v1/analytics/worker-utilization`: Worker slot capacity utilization (heatmap/grouped bar).
- `/api/v1/analytics/task-types`: Volume, success count, failure count, and success rate per registered task type.
- `/api/v1/analytics/queue-depth`: Backlog trends across queues.
- `/api/v1/analytics/oldest-task-age`: **SRS §14.4 Mandatory Requirement** exposing the age in seconds of the oldest pending task per queue, preventing hidden latency degradation.
- `/api/v1/brokers` & `/api/v1/brokers/{backend}/stats`: Segregated health and throughput metrics for Native PostgreSQL vs. Redis Streams adapters (SRS §7.3).

### 4. Correlation & Observability Headers (SRS §9, §13)
- `X-Request-ID` and `X-Trace-ID` are intercepted or generated by `CorrelationIdMiddleware`, bound to `structlog.contextvars` for structured JSON log context, and attached to every HTTP response.

## Consequences
- The full API surface is declared, documented in OpenAPI 3.1 (`/openapi.json`), and executable through Swagger UI (`/docs`).
- Any downstream consumer (SDK, CLI, or React frontend) can interact with the engine with full contract guarantees.
